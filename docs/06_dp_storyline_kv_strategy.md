# MCR DP 스토리라인 재구성 — KV 캐시 중심 4-DP 전개 (검토안 v0.1)

목적: 발표·과제 서사를 위해 DP를 **4개로 재선정·재배열**하는 제안 흐름
(DP1 KV 캐시 최적화 → DP2 근접연산 보완 → DP3 차세대 메모리 → DP4 유지보수
구조)의 타당성을 검토하고, 그 흐름에 맞는 신 DP 세트를 도출한다.
**Inference Orchestration 영역은 실무 범위(KV 재사용·압축 연구)를 반영해
스토리라인에서 배제**한다.

작성 기준: 확정안 v2 패키지 다이어그램([`01_architecture_overview.md`](01_architecture_overview.md)).
QA 정의는 [`00_qa_definitions.md`](00_qa_definitions.md) v0.9.
기존 DP 자산: DP1·DP2([`02`](02_design_points_dp1_dp2.md)) · DP3–DP5([`03`](03_design_points_dp3_dp5.md)) ·
DP6([`04`](04_design_points_dp6.md)) · DP7·DP8([`05`](05_design_points_dp7_dp8.md)).

> 본 문서는 **목록 합의용 검토안**이다 — 신 DP별 전체 전개(설계도 2종·QA
> 평가표 재채점·검토 노트)는 목록 확정 후 기존 문서 개정으로 수행한다.
> 혼동 방지를 위해 본 문서에서 신 번호는 **DP1′–DP4′**, 기존 번호는
> DP1–DP8로 표기한다.

---

## 1. 흐름 타당성 검토 — 결론: 타당하다. 단, 5가지 보완이 필요하다

### 1.1 이 흐름이 성립하는 이유 (강점)

1. **서사 구조가 진화 경로형이다**: SW 기법으로 성능을 얻고(DP1′) → 그
   기법의 잔여 비용을 자사 근접연산 HW로 회수하고(DP2′) → 그 HW 지원을
   1회성 특례가 아닌 일반 구조로 승격해 차세대 디바이스까지 수용하고(DP3′)
   → 전체를 생태계 위에서 지속 가능하게 유지하는 구조로 닫는다(DP4′).
   "문제 → 해결 → 해결의 한계 → 심화 해결 → 일반화 → 지속가능성"의 연쇄는
   리뷰어가 따라오기 쉽고, 매 단계가 사업 기여(자사 PIM/PNM/메모리 로드맵)에
   접지된다.
2. **QA 커버리지가 정확히 분담된다**: DP1′ → QA1(TTFT 축)·QA2·QA3,
   DP2′ → QA1(throughput 축)·QA2·QA4·QA5, DP3′ → QA4↔QA1,
   DP4′ → QA5·QA6↔QA1 상한. QA1의 2지표(v0.9: prefill/decode 축)가 DP1′과
   DP2′에 1:1로 대응하고, 6개 QA 전부가 최소 한 DP의 결정 변수로 등장한다 —
   "QA를 위해 억지로 만든 DP"가 없다.
3. **Orchestration 배제가 기존 자산과 정합한다**: orchestration 결합
   DP들(기존 DP2 정책 위치 · DP5 P/D 이동 · DP7/DP8 retrieval)이 빠지고,
   남는 기존 DP3(재사용)·DP6(근접연산)·DP4(tier 추상화)·DP1(스택 소싱)이
   신 DP1′–DP4′에 거의 1:1로 매핑된다. 실무 영역(재사용·압축)과 발표
   서사가 일치하고, 기존 문서의 후보구조·QA 평가·설계도가 대부분 재사용된다.

### 1.2 보완이 필요한 5가지

1. **DP1′의 범위 축소** — "KV 캐시 최적화"는 재사용·압축·배치가 뒤섞인
   범위라 순수형 후보 2개가 성립하지 않는다(자격 기준 1 위반). **재사용
   범위·복원 전략(기존 DP3)** 한 축으로 좁히고, 압축은 두 후보의 **공통
   기반으로 전제화**한다 — 압축 기법 선택(양자화 vs eviction)은 mechanism
   교체 수준이라 아키텍처 분기(자격 기준 4)가 아니고, scope 문서도 "압축
   mechanism은 기존 기법 채용"으로 이미 범위 외 선언했다.
2. **DP2′의 미결성 방어** — "PIM/PNM으로 DP1′ 한계를 해결한다"가 제목이면
   결론이 정해진 문서(자격 기준 3 위반)가 된다. 사용자 직관대로 general한
   이름이 맞고, 기존 DP6의 구도가 정답이다: PIM/PNM **사용 여부**가 아니라
   **"어디까지 내리는가"(오프로드 경계)** 를 쟁점으로 세우면 두 순수형
   후보(수치 경로 밖 vs 안)가 실제 trade-off로 갈린다. PIM/PNM이 이름에
   있어도 되는 이유: 두 후보 모두 PIM/PNM을 쓰므로 결론 선취가 아니다.
   또한 문제 정의를 **DP1′의 특정 채택안에만 의존하게 쓰지 않는다** —
   복원·해제·이동 연산의 GPU/host 잠식은 DP1′의 어느 후보를 채택해도
   존재하는 공통 압력이다(후보1 exact-prefix에서도 압축/해제 비용은 남는다).
   이렇게 써야 DP1′ 재결정 시 DP2′ 문서가 무효화되지 않는다.
3. **DP3′의 논리 방향 반전** — 기존 의존성 표는 "DP4(추상화) → DP6(오프로드):
   capability 미표현 시 오프로드 성립 불가"로, **논리 의존은 DP3′ → DP2′**
   인데 발표 순서는 반대다. 해결: DP3′ 문제 정의를 역방향으로 재서술한다 —
   "DP2′에서 채택한 근접연산 지원을 **1회성 특례(하드코딩)로 둘 것인가,
   capability로 일반화해 차세대 디바이스(HBF 영속·CMM-DC 공유·HBM4)까지
   재설계 없이 수용할 것인가**". 이 프레이밍은 발표 순서와 논리 순서를
   일치시키고, 오히려 "지원 방안 나열"이 아닌 구조 결정으로 DP를 세운다.
4. **DP4′의 결정 재정의** — 방법론상 스택 소싱(기존 DP1: 외부 vs 자체)은
   모든 DP의 실현 가능 집합을 제약하는 substrate라 맨 앞이 정석이다. 이를
   맨 뒤에 두려면 결정 내용을 바꿔야 한다: **"외부 스택(vLLM 계열) 위에서
   간다"는 전제(제약 C)로 격하**하고 — 실무 현실과 기존 DP1 검토 노트
   방향과도 일치 — DP4′는 그 위의 **통합 깊이**(확장점 격리 plugin vs 심층
   통합 fork)로 재정의한다. 이러면 미결 상태가 맞고, 마지막 배치가
   정당해진다: DP1′–DP3′ 채택안들이 요구하는 훅(비연속 KV 1급 관리, PIM
   커널 편입, capability tier)이 **확장점 안에서 수용 가능한가**가 결정
   변수이므로, 앞의 결정들이 쌓인 뒤에만 판정할 수 있는 DP다.
5. **Orchestration 배제의 뒤처리** — 그냥 빼면 구조도·QA 문서에 공백이
   남는다. §4의 제외 DP 처리(ADR 2건 + QA1 시나리오 개정)를 함께 수행해야
   한다. 특히 QA1 v0.9의 평가 시나리오는 "retrieval(SSD-PIM, ADR-001) 포함
   E2E"를 명시하고 TTFT bin 근거에 SmartANNS를 인용하므로, retrieval을
   범위에서 빼면 **QA 문서 v0.10 개정이 선행 조건**이다(TTFT 2× bin 자체는
   CacheBlend 2.2–3.3×만으로 유지 가능).

## 2. 신 DP 세트 (도출)

### DP1′. KV 캐시 재사용 범위·복원 전략 ← 기존 DP3

- **결정 질문**: 무엇을 어디까지 재사용하고, 위치가 어긋난 KV를 어떻게
  복원하는가. (압축은 두 후보 공통 기반 — 재사용 대상 KV는 tier에 압축
  상태로 존재한다는 전제를 공유.)
- **양방향 압력**: RoPE 위치 민감성으로 exact-prefix만 무손실 재사용 가능
  ↔ RAG·agent memory의 공유 기회는 대부분 비연속(CacheBlend TTFT 2.2–3.3×(B)).
  스토리지 dedup의 fixed vs content-defined chunking 논쟁과 동형.
- **후보구조**:
  - **후보1 — Exact-prefix 재사용 (block-aligned)**: prefix 해시 체인,
    복원 경로 없음. 품질 저하 구조적 0, 검증된 경로, 비연속 기회 포기.
  - **후보2 — 비연속 chunk 재사용 + selective recompute**: content-hash
    KV Index + 경계 토큰 부분 재계산 복원 파이프라인. 재사용률 상한 최대,
    품질 bound 관리·복원 비용 발생.
- **결정 변수**: 대표 워크로드에서 비연속 공유가 재사용 기회의 지배분인가
  (prefix vs chunk 히트율 실측).
- **QA 프로파일**: QA1 TTFT 축(후보2 ★★★ 상한/★★☆ 도달 리스크 vs 후보1
  ★★☆) ↔ QA2·QA4·QA5(후보1 우위). 기존 DP3 평가표 재사용.
- **서사 연결(→DP2′)**: 후보2 채택 시 selective recompute·해제·gather가
  GPU/host 임계 경로에 얹히고 tier 대역폭을 소비한다 — 이 **잔여 비용**이
  DP2′의 문제 정의로 넘어간다. (후보1 채택이어도 압축/해제·이동 비용은
  공통으로 남는다 — §1.2-2.)
- **재작업**: 소폭 — 쟁점 4의 "판단 주체는 DP2 종속" 문구를 Memory Engine
  내부 결정으로 개정(§4 ADR-002), "joint orchestration 연구 기여" 표현 재서술.

### DP2′. 근접연산(PIM/PNM) 활용 KV 데이터 경로 최적화 — 오프로드 대상·실행 구조 ← 기존 DP6

- **결정 질문**: KV 최적화(재사용·압축)가 남긴 데이터 경로 연산을 PIM/PNM에
  내릴 때, 오프로드 경계를 모델 수치 경로 **밖**까지로 하는가, **안**
  (decode attention)까지로 하는가.
- **양방향 압력**: decode wait 70–85%(A)·복원/해제 연산의 GPU 잠식(DP1′
  잔여 비용) + AttAcc 2.81×(B) ↔ 수치 경로 침범의 검증 부담(QA2)·attention
  변형별 커널 재작성(QA4)·툴체인 초기 비용(QA5). computational storage의
  오프로드 경계 논쟁과 동형.
- **후보구조**:
  - **후보1 — 데이터 관리 연산 오프로드 (수치 경로 밖)**: CompressionOp
    in-place 실행, scatter-gather·복원 재배치·eviction scoring을 PNM으로.
    DP1′ 복원 파이프라인의 실행 위치가 바로 이 대상 목록에 들어간다.
  - **후보2 — 모델 연산 오프로드 (decode attention을 PIM으로)**: AttAcc형
    이종 실행, Attention Engine에 PIM backend.
- **결정 변수**: 수치 경로 침범이라는 검증 비용의 단절점을 넘어야만 잡히는
  이득이 throughput 축 2×에 필수인가.
- **QA 프로파일**: QA1 throughput 축(후보2 ★★★ 상한 vs 후보1 ★★☆) ↔
  QA2·QA4·QA5(후보1 우위). 기존 DP6 평가표 재사용.
- **서사 연결(→DP3′)**: 어느 후보든 채택하면 "이 tier는 연산을 가진다"를
  구조가 표현해야 한다 — 이 표현을 특례로 둘지 일반화할지가 DP3′.
- **재작업**: 문제 정의 서두를 "DP1′ 채택안의 잔여 비용 회수"로 재서술
  (단 공통 압력 서술 유지 — §1.2-2), 명칭을 general형으로 확정.

### DP3′. 차세대 메모리 tier 추상화 수준 — 공통 파라미터 vs capability-aware ← 기존 DP4

- **결정 질문**: DP2′로 도입한 근접연산 지원을, 그리고 로드맵 디바이스
  (HBM4·CMM-DC·HBF)의 차별 속성(연산·공유·영속)을 — tier 특례 하드코딩으로
  두는가, capability 디스크립터로 일반화하는가.
- **양방향 압력**: "디바이스가 나올 때마다 재설계하지 않는 구조"(QA4 ★★★
  bin: 어댑터 ≤1모듈·코어 0) ↔ 수치 튜플(BW·용량·지연)로 표현 불가능한
  capability(NEAR_COMPUTE·PERSISTENT·SHARED)를 버리면 자사 차별 가치
  미회수. OS 블록 추상화 vs ZNS/DAX 논쟁과 동형.
- **후보구조**:
  - **후보1 — 공통 파라미터형**: 수치 프로파일 단일 코드 경로 + (DP2′
    채택분은 1회성 특례 처리). 이식성·검증 폭 최소, 차세대 capability
    구조적 미회수 — **DP2′ 채택안이 특례로 전락**.
  - **후보2 — Capability-aware 프로파일형**: 수치 튜플 + capability
    디스크립터, 정책이 capability를 질의. DP2′ 채택안이 1급 구조로 승격,
    스키마가 공개 인터페이스가 되는 비용.
- **결정 변수**: MCR의 존재 이유가 범용 이식 스택인가, 자사 디바이스 증명
  스택인가 (사업 전략 결정 — 상위 결정권자 입력 필요, 기존 DP4 검토 노트).
- **QA 프로파일**: QA4(후보1 ★★★ vs 후보2 ★★☆) ↔ QA1 throughput
  축(후보2 ★★★ vs 후보1 ★★☆)·QA5. 기존 DP4 평가표 재사용.
- **재작업**: 문제 정의를 역방향(DP2′ 채택의 일반화)으로 재서술(§1.2-3),
  DP5 커플링(SHARED→공유 스테이징) 문구는 범위 외 이관에 맞춰 축소.

### DP4′. Baseline framework 위 통합 구조 — 확장점 격리 vs 심층 통합 ← 기존 DP1 재프레이밍

- **전제(제약 C)**: 실행 스택은 외부 생태계(vLLM 계열)를 채택한다 — 기존
  DP1의 "외부 vs 자체"는 본 스토리라인에서 전제로 격하하고 ADR-002로 기록
  (§4). 독립 framework 재구현·추종 비용(수십 인월+, QA5 ★☆☆)이 근거.
- **결정 질문**: DP1′–DP3′의 채택안(비연속 KV 1급 관리 · PIM 커널 실행 ·
  capability tier)을 baseline framework 위에 얹을 때 — **공식 확장점
  안에서 어댑터로 격리**하는가, **fork하여 코어를 수정**하는가.
- **양방향 압력**: upstream 2주 릴리스 추종·rebase 비용(fork는 6–12개월 후
  급증(C))·framework 교체 헤지(QA6) ↔ 확장점의 구조적 제약 — block table
  밖 비연속 KV는 2급 시민, scheduler가 tier·PIM 실행 비인지, connector
  API의 용도 제한(기존 DP1 문제 정의의 구조적 한계 3종이 그대로 이 압력).
- **후보구조**:
  - **후보1 — 확장점 격리형 (plugin/adapter)**: connector·custom backend
    등 공식 확장점만 사용, framework 결합 코드를 어댑터 계층에 격리(QA6
    ★★★ 경로: 결합 ≤10%·코어 변경 0). 앞선 DP 채택안 중 확장점 밖 요구는
    upstream 기여 또는 기능 축소로 수용.
  - **후보2 — 심층 통합형 (fork)**: scheduler·block table 코어 수정 허용 —
    비연속 KV 1급 관리·PIM 스케줄 인지를 정면 구현. 기법 자유도·성능 상한
    최대, rebase·회귀 검증 상시 부담(QA5 ≤2 FTE 리스크)·교체 비용 증가.
- **결정 변수**: DP1′ 후보2·DP2′ 후보2의 요구 훅이 확장점 안에서 실제로
  수용되는가 (결합부 정적 분석 + 파일럿 포팅으로 판정 — QA6 측정 방법 그대로).
- **QA 프로파일**: QA5·QA6(후보1 ★★★ vs 후보2 ★☆☆~★★☆) ↔ QA1 상한·기법
  자유도(후보2 우위). 기존 DP1 후보1(변형 A/B 델타 표 포함)·후보2 자산에서
  plugin vs fork 구분("주의" 문단)을 후보 축으로 승격해 재작성.
- **재작업**: 중폭 — 기존 DP1 문서의 결정 축 재정의. 설계도는 dp1
  다이어그램의 부분 재활용 가능.

## 3. 서사 흐름 요약 (발표용 한 줄씩)

| 순서 | DP | 한 줄 서사 | 담당 QA 축 |
|---|---|---|---|
| DP1′ | KV 재사용 범위·복원 전략 | SW 기법으로 prefill을 연다 — 단 복원 비용이 남는다 | QA1-TTFT · QA2 · QA3 |
| DP2′ | 근접연산 활용 KV 데이터 경로 최적화 | 남은 비용을 자사 근접연산으로 회수한다 — 경계를 어디에 긋나 | QA1-throughput · QA2 · QA5 |
| DP3′ | 차세대 메모리 tier 추상화 수준 | 그 지원을 특례가 아닌 구조로 — 로드맵 디바이스까지 | QA4 ↔ QA1 |
| DP4′ | Baseline framework 통합 구조 | 전부를 생태계 위에서 지속 가능하게 | QA5 · QA6 ↔ QA1 상한 |

자격 기준 검증: 4개 DP 모두 ① 양립 불가 순수형 2후보 ② QA 프로파일이
실제로 갈림(각 행 별점 상이) ③ 미결 ④ 아키텍처 수준(패키지·인터페이스
배치 영향) — 통과. 전 QA 우위 후보가 있는 DP 없음.

## 5. 신 DP 간 의존성

| 의존 | 내용 |
|---|---|
| DP1′ → DP2′ | DP1′ 채택안이 DP2′ 후보1의 오프로드 대상 목록을 결정(후보2 채택 시 selective recompute·복원 재배치가 추가). 단 압축/해제·이동 비용은 DP1′ 양 후보 공통 — DP2′ 성립 자체는 DP1′ 결론에 비종속 |
| DP3′ ⇄ DP2′ | **논리 의존은 DP3′ → DP2′**(capability 미표현 시 오프로드가 특례 하드코딩으로만 성립 — 기존 DP4→DP6 커플링). 발표 순서는 역방향이므로 DP3′ 문제 정의를 "DP2′ 채택의 일반화"로 서술해 정합(§1.2-3). DP3′ 후보1 채택 시 DP2′ 채택안은 특례로 유지되나 차기 디바이스 확장 불가 |
| DP1′·DP2′·DP3′ → DP4′ | 세 채택안의 요구 훅(비연속 KV 1급 관리 · PIM 커널 편입 · capability tier)이 DP4′ 후보1(격리형)의 실현 가능성 판정 입력 — DP4′가 마지막인 이유 |
| DP4′ → DP2′ | 격리형 확정 시 DP2′ 후보2(attention 오프로드)의 통로가 custom attention backend 확장점으로 제한 — scheduler 비인지로 파이프라인 효율 제약(기존 DP1→DP6 커플링 계승). 역방향 제약이므로 DP4′ 판정 시 DP2′ 채택안과 상호 검증 |
| 공통 전제 | ADR-002(Memory Engine 자율 정책 + 외부 스택 전제) · KV Index·CompressionOp 의존 역전(확정안 v2) |
