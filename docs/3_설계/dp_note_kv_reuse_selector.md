# [검토 대기 노트] KV 재사용 — 재계산 토큰 선택기의 실행 구조 (v0.1)

**상태: 검토 대기** — DP 확정 아님. KV 재사용 DP 전개 시 후보구조의 입력
자료로 재검토한다. (작성 배경: DP 상세화 논의 중 도출된 프레이밍을 보존.
현 DP 체계에서 재사용 DP의 번호는 추후 확정.)

## 0. 맥락 — 팀 연구와 구조 설계의 관계

- 팀의 실제 연구: **non-contiguous KV 재사용 알고리즘** — CacheBlend(문맥
  +query의 부분 QKV 연산으로 K/V deviation을 구해 재계산 토큰 선정)를
  baseline으로, Prophet류(문맥×query의 attention 연산으로 선정) 등 개선
  알고리즘을 연구 중. **이 계열은 대부분 query-aware** — 요청 시점에
  query를 봐야 선택이 가능하다.
- 방법론 정리: 선택 알고리즘 자체는 **mechanism(교체 가능한 모듈)이라 DP가
  아니다**. DP가 되는 것은 그 알고리즘 패밀리를 수용하는 **구조** — 즉
  "선택기가 엔진의 무엇을 보고, 어디서·언제 실행되는가"의 결정.
- 서사: **알고리즘 연구 = 세입자, 아키텍처 = 집.** 설계 산출물은 "어떤 선택
  알고리즘이 이기든 갈아 끼우고, 요청별 예산으로 조율하고, ΔF1 bound를
  검증할 수 있는 런타임 구조". 알고리즘 채택·교체는 ADR로 기록, 팀
  알고리즘의 실측(ΔF1·TTFT)이 QA 수치와 DP 채택 근거로 유입.

## 1. 폐기된 후보 프레이밍 2건 (사유 기록)

| 폐기 후보 | 내용 | 폐기 사유 |
|---|---|---|
| 문헌 기법 비교형 (prefix caching vs CacheBlend) | 두 기존 기법을 후보로 대결 | ① 자체 설계안이 없음 ② CacheBlend가 prefix의 상위 호환이라 결정이 자명 — DP 자격(실질 trade-off) 미달 |
| 사전 가공형 (store-time fused pre-blend) | 인기 chunk **조합**을 유휴 시간에 미리 blending한 fused 사본을 상위 tier 상주 | **조합 단위 사본 = 조합 폭발 + dedup 파괴** — 유효 용량 잠식으로 목표 2(메모리 효율)와 정면 충돌 (검수 지적) |
| 경량 시그니처 계약형 (query-독립 메타데이터) | 저장 시점에 chunk별 민감도 시그니처를 계산, 온라인은 lookup만 | **알고리즘 패밀리가 query-aware인데 query를 볼 수 없는 계약** — 연구 대상 전부를 수용 불가한 허수아비 후보 (검수 지적) |

## 2. 검토 대기 프레이밍 — query-aware 선택 연산의 실행 구조

query-aware는 전제(온라인 연산 불가피). 갈리는 것은 **선택 연산을 어디서·
언제 실행하나**:

### C1. 본체 융합형 (in-engine, exact)

- **구조**: 선택 연산을 prefill **본체의 1층 연산과 융합** — 실제 K/V
  deviation·attention 스코어를 그대로 선택 근거로 사용, 2층부터 선택
  토큰만 재계산(로딩과 중첩). CacheBlend 구현 계열 — TTFT 2.2–3.3×(B)가
  이 구조의 실측 앵커. selector 훅은 엔진 실행 루프(layer 경계) 내부.
- **시나리오**: 요청 도착 → prefill 시작 → 1층 결과로 "이 query가 주목하는
  토큰 12%" 확정 → 이후 층은 그 토큰만 재계산.
- 장점: 선택 근거 = 실제 모델 연산(근사 오차 0 — QA2 최선), 검증된
  방식(실측 앵커). 단점: 엔진 코어 배선(릴리스 추종·교체 리스크 — QA5),
  선택 연산이 피크 GPU 임계 자원 소비(QA1).

### C2. 경량 선행형 (proxy, speculative)

- **구조**: retrieval 직후(= prefill 시작 전, query는 이미 존재) **경량
  proxy**(축소 모델/저차원 근사, CPU·보조 스트림)로 선택을 선행 계산 —
  엔진 밖 독립 컴포넌트. prefill 시작 시점에 재계산·로딩 계획이 이미
  확정되어 로딩∥재계산∥prefetch 파이프라인 최대화.
- **시나리오**: retrieval 반환 즉시 정찰(근사 attention) → 계획 확정 →
  본 게임(prefill)은 계획대로만 실행.
- 장점: 엔진 무수정(proxy만 교체 — 알고리즘 릴리스 트랙과 정합, QA5),
  선택 연산이 GPU 임계 경로 밖(QA1), 선행 확정의 파이프라인 이득.
  단점: **근사 오차** — 정찰이 틀리면 엉뚱한 토큰 재계산(ΔF1 리스크),
  방어하려면 재계산율 보수 상향 → TTFT 반납(QA2↔QA3 연쇄), proxy 재교정
  관리(모델 변경 시).

### QA 대비 (F, 잠정)

| | C1 본체 융합형 | C2 경량 선행형 |
|---|---|---|
| QA1 (피크 자원) | ★★☆ | **★★★** |
| QA2 (품질) | **★★★** (정확 근거) | ★★☆ (근사 오차) |
| QA3 (TTFT) | **★★★** (실측 앵커) | ★★☆ (상한↑ / 도달 리스크) |
| QA5 (진화성) | ★★☆ (코어 훅) | **★★★** (proxy 교체) |

- **동형성**: CPU branch prediction / speculative execution.
- **결정 변수**: 경량 근사의 선택 일치율(실제 1층 선택과의 겹침)이 ΔF1
  bound를 지킬 만큼 높은가 — **팀 알고리즘 연구가 실측으로 답할 질문**
  (자체 개선안이 근사 가능한 형태인지 포함).
- **직교 축(유지 확정)**: SLO/품질 예산 기반 **동적 재계산율
  컨트롤러**("얼마나 재계산하나"의 정책) — 두 후보 모두에 결합 가능,
  QA2 요청별 bound 집행의 실현 수단.
- hybrid 후보(시그니처로 1차 후보 축소 + probe는 그 위에만)는 검토
  노트감 — 순수형 후보로 세우지 않는다.

## 3. 재검토 시 확인할 것

1. C2의 proxy 실현 방식(축소 모델 / 저차원 사영 / 근사 attention)별 선택
   일치율 — 팀 실측 필요.
2. Prophet류 알고리즘의 정확한 명칭·출처 — 문헌 앵커(B) 등재.
3. 엔진(vLLM 등) 확장점에서 layer-경계 훅의 실현 가능성 — 실행 스택
   소싱 DP의 결과에 종속.
